# YouGile AI Agent

Автономный AI-агент для автоматизации бизнес-задач: принимает задачи из почты и Telegram,
самостоятельно выполняет их через GLM-4.5 Flash, создаёт документы, загружает их
в хранилище (по умолчанию MongoDB, опционально Cloudflare R2) и отчитывается в YouGile.

## 🔧 Инструменты агента

Актуальный реестр всегда виден на веб-дашборде (блок «Инструменты агента») — он
собирается прямо из `tools.js`, которым кормят модели.

| Инструмент | Назначение |
|---|---|
| `web_search(query, maxResults?)` | Поиск в интернете. Цепочка провайдеров, кэш на 7 дней. Если ничего не сработало — модель получает явный запрет выдумывать данные |
| `web_analysis(url, question?)` | Чтение конкретной страницы. Tavily Extract → собственное извлечение из HTML. С параметром `question` возвращает готовый ответ и ключевые факты |
| `analyze_image(...)` | Разбор изображения vision-моделью (GLM-4.6V) |
| `keyword_research(seed)` | Сбор ключевых слов из подсказок Yandex/Google/DuckDuckGo (частотности НЕТ — их снимает владелец) |
| `semantics_draft(groups, expand?)` | Черновик семантики из каталога владельца + заявка на согласование |
| `semantics_status(draftId?)` | Статусы черновиков и заявок |
| `site_page_create(draftId, cluster, kind?)` | Создание страницы-черновика в MODX (published=0). Работает ТОЛЬКО по одобренному черновику — гейт внутри инструмента |
| `seo_audit(url, urls?)` | Механический SEO-аудит: мета-теги, H1-H6, скорость, мобильность, микроразметка, robots/sitemap; балл и находки с рекомендациями |
| `create_document(format, filename, title?, content?, tables?)` | Создание документа и загрузка в хранилище. Возвращает ссылку для комментария к задаче |
| `save_result(taskId, step, data)` | Сохранение промежуточного результата в MongoDB |
| `add_comment(taskId, text)` | Комментарий в чат задачи YouGile (HTML экранируется) |
| `update_task_status(taskId, status)` | Перемещение задачи: `Выполняется` / `На проверку` / `Готово` / `Ошибка` |

## ☁️ Облачное хранилище

Провайдер выбирается переменной `CLOUD_PROVIDER` (`mongo` | `r2` | `pcloud` | `none` | `auto`),
весь остальной код работает через единый модуль `lib/cloud.js`, поэтому смена
хранилища — вопрос одной переменной окружения.

### Вариант по умолчанию: `mongo` — без внешних сервисов и без карты

Документы сохраняются в ту же MongoDB, на которой работает агент, и раздаются
через подписанные ссылки `https://<сервис>/files/<подпись>/<имя>?k=<ключ>`.

- не нужно ни аккаунтов, ни платёжных карт, ни активации подписок;
- ссылка постоянная (не истекает, как presigned URL) и приватная: без подписи
  файл не получить, а подпись нельзя подделать для другого файла;
- ограничение — 512 МБ на бесплатном тарифе Atlas: при среднем документе
  ~100 КБ это тысячи файлов;
- минус один: при первом открытии ссылки спящий dyno Render просыпается
  ~30–60 секунд.

Достаточно трёх переменных, которые у вас уже есть: `MONGODB_URI`,
`PUBLIC_BASE_URL`, `ADMIN_TOKEN`. Ничего дополнительно настраивать не нужно.

### Cloudflare R2

Почему R2, если нужна карта:

- **10 ГБ бесплатно**, исходящий трафик тоже бесплатный (у AWS S3 он платный);
- API-токен создаётся в дашборде **за минуту, без писем в поддержку**;
- публичные ссылки раздаёт CDN Cloudflare, а не спящий dyno Render —
  документ открывается мгновенно, без холодного старта в 30–60 секунд;
- бакет можно оставить **приватным**: тогда файлы раздаются через наш сервер
  по подписанным ссылкам без срока действия.

### Шаг 1. Активировать подписку R2 (нужна платёжная карта)

Storage & databases → R2 Object Storage → **Add R2 subscription to my account**
(«Total Due Now $0.00»: бесплатно в пределах 10 ГБ и лимитов операций, но Cloudflare
требует привязать карту). Без этого шага кнопка **Create bucket** не появляется.

### Шаг 2. Создать бакет

1. [dash.cloudflare.com](https://dash.cloudflare.com) → **R2 object storage**
2. **Create bucket** → имя, например `yougile-docs`
3. Юрисдикцию можно оставить по умолчанию (для EU выберите `EUR`)

### Шаг 3. Создать API-токен

1. На странице R2 справа в разделе **Account details** → **Manage** рядом с **API Tokens**
2. **Create Account API token**
3. **Permissions** → `Object Read & Write`
4. **Specify bucket** → выбрать созданный бакет
5. **Create Account API token**

На следующем экране появятся **Access Key ID** и **Secret Access Key**.
Secret показывается **один раз** — скопируйте сразу. Там же виден `Account ID`.

### Шаг 4. Выбрать способ отдачи ссылок

**Вариант A — приватный бакет (рекомендуется для бизнес-документов).**
Ничего настраивать не нужно. Ссылки вида

```
https://<ваш-сервис>.onrender.com/files/<подпись>/<имя>?k=<ключ>
```

Подпись — HMAC-SHA256 от ключа объекта на `ADMIN_TOKEN` (или `FILES_SECRET`).
Файл доступен только обладателю ссылки, подделать подпись для другого файла нельзя,
срок действия не ограничен — важно, потому что ссылки попадают в комментарии задач,
которые читают спустя недели.

**Вариант B — публичный бакет (быстрее, ссылки на CDN).**
Buckets → ваш бакет → **Settings**, затем одно из двух:

- **Custom domain** → *Add* → например `files.example.com`
  (домен должен быть добавлен в тот же аккаунт Cloudflare). Даёт кэш, WAF и
  защиту от ботов.
- **Public development URL** → *Enable* → ввести `allow`.
  Проще, но Cloudflare ограничивает этот режим по трафику и не рекомендует
  для продакшена.

Полученный адрес положите в `R2_PUBLIC_BASE_URL`.

### Шаг 5. Переменные окружения на Render

```
CLOUD_PROVIDER=r2
R2_ACCOUNT_ID=<Account ID>
R2_ACCESS_KEY_ID=<Access Key ID>
R2_SECRET_ACCESS_KEY=<Secret Access Key>
R2_BUCKET=yougile-docs

# только для варианта B:
R2_PUBLIC_BASE_URL=https://files.example.com

# только если бакет создан в юрисдикции EU/US/FedRAMP:
R2_JURISDICTION=eu
```

При старте приложение проверяет хранилище и пишет в лог либо
`✅ Cloudflare R2 подключен: бакет "yougile-docs" (раздача через сервер)`,
либо конкретную причину отказа. Состояние видно и на дашборде.

### Типичные ошибки

| Симптом | Причина |
|---|---|
| `NoSuchBucket` | Неверное `R2_BUCKET`, либо не указана `R2_JURISDICTION` для бакета в EU |
| `AccessDenied` | Токен создан без права `Object Read & Write` или не на тот бакет |
| `InvalidAccessKeyId` | Неверный `R2_ACCESS_KEY_ID` |
| `SignatureDoesNotMatch` | Неверный `R2_SECRET_ACCESS_KEY` |
| `getaddrinfo ENOTFOUND` | Неверный `R2_ACCOUNT_ID` |

Все сообщения переводятся в понятные подсказки — см. `r2-client.js → diagnose()`.

### Про pCloud

Клиент pCloud в проекте остался (`pcloud-client.js`), но **работать не будет
без OAuth2-токена**. В апреле 2026 pCloud отключил авторизацию по логину и паролю
и отозвал все ранее выданные ею токены; поддержка подтвердила, что изменение
постоянное. OAuth-приложение нельзя создать самостоятельно — только по запросу
в поддержку pCloud, и они выдают `Client ID` и `Client Secret`.

Если получите OAuth2-токен — положите его в `PCLOUD_AUTH_TOKEN` и выставите
`CLOUD_PROVIDER=pcloud`. Полученный токен работает с файловыми операциями
(`uploadfile`, `getfilepublink`), то есть ровно с тем, что нужно агенту.

Утилита `npm run pcloud:token` оставлена для истории, но с апреля 2026
возвращает ошибку — парольная авторизация больше не принимается.

Google Drive удалён из проекта: Service Account не имеет собственной квоты
хранилища, поэтому загрузка падала.

## 🌐 Публикация на сайт (MODX)

Агент создаёт страницы на **rocket-up.space** (MODX Revolution 2.8.x) через коннектор
[`modx/ai-publisher.connector.php`](modx/ai-publisher.connector.php) — инструкция по установке
(5 минут) в шапке этого файла. Пока `MODX_PUBLISHER_URL`/`MODX_PUBLISHER_TOKEN` пусты,
инструменты публикации отключены.

**Переменные на Render:**

| Переменная | Значение |
|---|---|
| `MODX_PUBLISHER_URL` | `https://rocket-up.space/assets/components/aipublisher/connector.php` |
| `MODX_PUBLISHER_TOKEN` | Та же строка, что в настройке MODX `ai_publisher_token` (Система → Настройки) |
| `MODX_TEMPLATE_PROMO` / `MODX_PARENT_PROMO` | Шаблон и родитель страниц продвижения (по умолчанию `4` / `6` — сверить с сайтом) |
| `MODX_TEMPLATE_ARTICLE` / `MODX_PARENT_ARTICLE` | То же для статей блога (по умолчанию `3` / `3`) |
| `MODX_AUTO_PUBLISH` | `false` — страницы создаются непубликованными черновиками, публикует человек |

**Два контура защиты существующего контента:**

1. **Серверный:** режим коннектора `create_only` (по умолчанию) — `update`/`publish` чужих ресурсов отклоняются с `403` даже при верном токене. Переключение в `full` — только настройкой MODX `ai_publisher_mode`, осознанно владельцем. Действия `delete` в коннекторе нет и не будет.
2. **Агентский:** `lib/modx-client.js` не отправляет такие запросы без одобренной заявки из `lib/approvals.js` — вместо действия создаёт заявку и уведомляет владельца в Telegram (`/approve <id>`).

Принадлежность агенту помечается в `properties` ресурса, поэтому он свободно доводит
до ума собственные черновики, а защита переживает рестарты.

**Проверка состояния:** команда `/modx` в Telegram-боте либо `GET /api/modx/status`
с заголовком `X-Admin-Token`. При старте приложение пишет в лог `✅ MODX на связи: v…, режим …`.

**Типичные ошибки** (`lib/modx-client.js → diagnose()`): `401` — токен не совпал с настройкой
MODX; `403` — сработала политика `create_only`; `404` — неверный URL коннектора; `412` —
анти-бот защита хостинга блокирует запросы с датацентровых IP (нужно исключение для пути коннектора).

## 🔐 Whitelist Telegram-бота

Бот принимает команды не от всех подряд: любой, кто найдёт бота по имени, раньше мог
создавать задачи в вашем YouGile.

### Как устроен доступ

Есть два независимых источника прав:

1. **`TELEGRAM_ADMIN_IDS`** — переменная окружения, chat ID через запятую.
   Это неотзываемые администраторы: команду `/deny` на них применить нельзя.
   Защита от случайной блокировки самого себя.
2. **Список доступа в MongoDB** — правится командами бота, без передеплоя.

Режим **строгий** включается автоматически, как только задан `TELEGRAM_ADMIN_IDS`
или в базе появилась хотя бы одна запись. До этого бот работает в **открытом** режиме —
специально, чтобы нельзя было потерять доступ сразу после деплоя; при этом он
предупреждает в логах и присылает сообщение в чат.

### Как выдать доступ другому человеку

Человек пишет боту что угодно и получает отказ вместе со своим chat ID:

```
🔒 Доступ запрещён
Ваш chat ID: 123456789
Передайте администратору команду: /allow 123456789
```

Одновременно вам приходит уведомление с готовой командой. Дальше:

| Команда | Действие |
|---|---|
| `/allow 123456789` | Разрешить доступ по ID |
| `/allow ivan` | Разрешить доступ по username из очереди запросов |
| `/deny 123456789` | Отозвать доступ (не действует на админов из `TELEGRAM_ADMIN_IDS`) |
| `/who` | Кто имеет доступ + очередь запросов |

Доступ выдаётся бессрочно и переживает рестарты — он хранится в базе, а не в памяти процесса.

### Команды бота

| Команда | Назначение |
|---|---|
| `/task <текст>` | Создать задачу в YouGile |
| `/status` | Счётчики по колонкам + статистика базы |
| `/reset <taskId>` | Снять блокировку с задачи, чтобы агент взял её заново |
| `/who` | Кто имеет доступ + очередь запросов доступа |
| `/allow <chatId или username>` | Разрешить доступ к боту |
| `/deny <chatId>` | Отозвать доступ у пользователя (не действует на админов из `TELEGRAM_ADMIN_IDS`) |
| `/drafts` | Черновики семантики: id, статус и id заявки на одобрение |
| `/approvals` | Заявки на согласование, ожидающие решения |
| `/approve <id заявки>` | Одобрить заявку (например, разблокировать создание страниц по черновику) |
| `/deny <id заявки>` | Отклонить заявку на согласование (id — 8 hex-символов; бот сам отличает заявку от chatId/username) |
| `/modx` | Состояние коннектора публикации MODX: версия, режим политики, сайт |
| `/start`, `/help` | Справка и ваш chat ID |
| `.xlsx` с частотностями | Импорт частотностей в черновик семантики: reply на уведомление, кнопка под ним или просто файл (если черновиков несколько — бот спросит, куда отнести) |
| *(просто текст)* | Создать задачу из сообщения |

## 📊 Веб-дашборд

`https://<ваш-сервис>.onrender.com/` — при первом входе попросит `ADMIN_TOKEN`
(хранится в localStorage браузера, передаётся заголовком `X-Admin-Token`).

Разделы:

- **Предупреждения** — незаполненные критичные переменные окружения
- **Метрики** — задач выполнено / с ошибками / в работе, шаги, кэш поиска, аптайм
- **Сервисы** — MongoDB, GLM, облако (бакет и режим отдачи ссылок), провайдеры поиска,
  Telegram (режим whitelist), YouGile, почта
- **Колонки YouGile** — счётчики задач
- **Запуски агента** — режим, шаги, вызовы инструментов, длительность, итог, ошибка
- **Реестр задач** — статус, число попыток, кнопка сброса блокировки
- **Последние шаги** — чем агент занимался
- **Доступ к боту** — список и очередь запросов
- **Процесс** — память (RSS, heap), load average, Node.js, часовой пояс

Автообновление каждые 30 секунд. Дашборд собран без внешних зависимостей и CDN —
работает даже при недоступности сторонних хостов.

## 🔄 Workflow

### Задача из письма

```
Письмо с темой «[TASK] ...»
  → IMAP IDLE срабатывает мгновенно (поллинг каждые 2 мин как страховка)
  → GLM разбивает письмо на отдельные задачи
  → задачи создаются в колонке «Входящие задачи»
  → письмо помечается прочитанным и переносится в AI_DONE
  → уведомление в Telegram
```

### Выполнение

```
Задача перемещена в «В работе» (сценарии конвейера из Telegram попадают туда сами)
  → task-executor замечает её (опрос каждые 30 с)
  → блокировка в MongoDB: повторный запуск невозможен даже после рестарта,
    поэтому очередь и выполнение совмещены в одной колонке
  → комментарий о старте
  → сценарий конвейера (семантика / страница / SEO-аудит) ИЛИ свободный агент:
    специализированный промпт + цикл шагов «инструмент → save_result»
  → комментарий с результатом и ссылками на документы
  → файлы документов дополнительно загружаются в хранилище YouGile
    (POST /api-v2/upload-file) — ссылка на копию публикуется в чате задачи
  → успех: статус «На проверку» (владелец проверяет и переносит в «Готово»)
  → провал: статус «Ошибка» (оттуда можно вернуть в «В работе»)
  → уведомление в Telegram: КОРОТКОЕ — одна строка статуса и ссылка на
    страницу отчёта https://<сервис>/report/<id задачи> (полный текст — в
    комментарии YouGile и на странице отчёта, в Telegram не дублируется)
```

### Схема доски (5 колонок)

```
Входящие задачи → В работе → На проверку → Готово
                      └────────→ Ошибка ──┘ (возврат в «В работе» вручную)
```

| Колонка | Env-переменная | Роль |
|---|---|---|
| Входящие задачи | `COLUMN_DEFAULT` | Все новые задачи (Telegram, почта). Триаж: что берёт агент, что человек |
| В работе | `COLUMN_TO_EXECUTE` | Очередь-триггер: исполнитель забирает отсюда задачи; во время выполнения задача остаётся здесь (защита от двойного захвата — блокировка в MongoDB) |
| На проверку | `COLUMN_REVIEW` | Выполненные задачи ждут ручной проверки владельцем. Без этой переменной — откат сразу в «Готово» |
| Готово | `COLUMN_DONE` | Проверено и принято |
| Ошибка | `COLUMN_ERROR` | Не выполнено; можно вернуть в «В работе» (или /reset + повтор) |

Колонка «Ожидает подтверждения» из схемы исключена (`COLUMN_AWAITING_CONFIRMATION` удалён).

### Семантика: черновик → частотности → одобрение

```
«Собери черновик семантики по группе X»
  → задача сама уходит в «В работе» (сценарий конвейера)
  → черновик: только запросы владельца из каталога (расширение подсказками
    выключено — SEMANTICS_SUGGEST_EXPAND=false; кандидата из подсказок
    владелец признал нерелевантными)
  → файл .xlsx в хранилище, ссылка — в комментарии задачи; в Telegram
    приходит короткая строка и ссылка на страницу отчёта /report/<id>
  → заявка на согласование (id из 8 символов)
  → владелец присылает .xlsx боту: либо свой файл со строками «Группа: …»,
    либо файл черновика от бота. Файл = истина: запросы группы заменяются
    строками файла, чужие группы пропускаются с отчётом
  → /approve <id заявки> → страницы по черновику разрешены
```

Привязка присланного файла к черновику — детерминированная, по приоритетам:

1. **Ответ (reply)** на уведомление бота о черновике или заявке — самый надёжный способ;
2. **Кнопка «Загрузить частотности»** под уведомлением: нажал → прислал файл;
3. **Подпись** к файлу: id черновика (8 hex) или id задачи YouGile (uuid);
4. **Единственный** черновик в статусе «ожидает».

Если сигналов нет, а ожидающих черновиков несколько — бот НЕ угадывает: запоминает
файл и спрашивает кнопками, к какому черновику его отнести.

### Вопрос в чате задачи

```
Пользователь пишет вопрос в чат ВЫПОЛНЕННОЙ задачи
  → YouGile присылает вебхук
  → сервер сразу отвечает 200 (обработка идёт в фоне)
  → дедупликация по messageId в MongoDB — ретраи YouGile не дают дублей
  → агент читает последние 10 сообщений чата
  → отвечает по существу, при необходимости ищет в интернете
```

## 🖥️ Деплой на Render

1. Подключите репозиторий к Render → **New → Web Service**
2. **Build Command:** `npm ci` — использует `package-lock.json`, сборка воспроизводима
3. **Start Command:** `npm start`
4. Заполните переменные окружения (см. `.env.example`)
5. Обязательно задайте `ADMIN_TOKEN` и `TELEGRAM_ADMIN_IDS`
6. Настройте cron-job.org, чтобы бесплатный dyno не засыпал:
   ```
   URL:      https://<ваш-сервис>.onrender.com/health
   Schedule: */5 * * * *
   ```

`/` и `/health` всегда отвечают `200` и не обращаются к внешним сервисам,
поэтому подходят для пинга.

### Как изменения попадают в прод

Изменения пушит **сам AI-ассистент** прямо из чата в репозиторий `blik-byte/YouGile-GLM`
(ветка `main`), дальше Render передеплоивает сервис автоматически. Каждый push в `main` = пересборка.

**Что нужно ассистенту — fine-grained PAT от владельца (создание занимает 2 минуты):**

1. Открыть 👉 https://github.com/settings/personal-access-tokens/new
   (или: аватар → Settings → внизу Developer settings → Personal access tokens → Fine-grained tokens → Generate new token)
2. **Token name:** `qwen-push`; **Expiration** — длительный срок (90–365 дней): истёкший токен даёт `401 Bad credentials` при пуше, и его нужно пересоздать
3. **Repository access:** Only select repositories → `blik-byte/YouGile-GLM`
4. **Permissions → Repository permissions → Contents:** **Read and write**
5. **Generate token** → скопировать (`github_pat_…`) → вставить в чат ассистенту

Ассистент пушит через `https://x-access-token:<ТОКЕН>@github.com/blik-byte/YouGile-GLM.git`,
автор коммита — `YouGile AI Agent`. Токен — секрет: в репозиторий и README он НЕ попадает.
Если push отвечает 401/403 — токен истёк или отозван, нужно пересоздать по той же инструкции.

**Проверка после пуша:** https://yougile-glm.onrender.com/health — 200 и «свежий»
`uptimeSec` (отсчитывается от момента деплоя); затем логи Render и веб-дашборд.

После изменения кода или завершения этапа обновляйте раздел «📍 Текущее состояние» в начале README.

### Часовой пояс

Контейнеры Render живут в **UTC**. Ежедневный отчёт считается по переменной
`REPORT_TZ` (по умолчанию `Europe/Moscow`), поэтому приходит в 9:00 по Москве.
Чтобы и логи были в местном времени, добавьте переменную `TZ=Europe/Moscow`.

## ⚠️ Важные особенности реализации

**Таймауты.** У всех внешних запросов есть таймаут (по умолчанию 30 с,
`HTTP_TIMEOUT_MS`). В Node.js `fetch` не имеет таймаута по умолчанию: один зависший
запрос навсегда блокировал почтовый воркер.

**Блокировки задач.** Состояние выполнения хранится в MongoDB, а не в памяти.
Рестарт Render больше не приводит к повторному выполнению задач из колонки,
а упавшая задача повторяется до `TASK_MAX_ATTEMPTS` раз с cooldown.

**Дедупликация вебхуков.** По уникальному индексу в MongoDB с TTL 1 час —
переживает рестарты и любые интервалы повторных доставок YouGile.

**Идемпотентная подписка на вебхуки.** Перед созданием проверяется список
существующих подписок: раньше каждый деплой добавлял дубль, и сообщения
обрабатывались несколько раз.

**Обрезка контекста.** История диалога с GLM урезается под бюджет
(`GLM_MAX_CONTEXT_CHARS`): system-промпт и хвост сохраняются, старые сообщения
выбрасываются с явной пометкой для модели.

**Экранирование HTML.** Все динамические значения экранируются перед вставкой
в комментарии YouGile и уведомления Telegram. Ранее символ `<` в заголовке задачи
приводил к `Can't parse entities`, и уведомление молча терялось.

**Скачивание файлов из Telegram.** `getFile` может временно отказать сразу после
отправки файла (`wrong file_id or the file is temporarily unavailable`) — скачивание
выполняется с ретраями и проверкой HTTP-статуса. «Запомненные» file_id (когда бот
спрашивает, к какому черновику отнести файл) со временем истекают: при сбое бот
просит прислать файл заново и сохраняет выбранный черновик, а не теряет его.

## 🐛 Известные ограничения

1. **Бесплатный тариф Render засыпает** через 15 минут простоя → нужен пинг cron-job.org.
2. **Один процесс.** Все воркеры живут в одном dyno: при его рестарте прерывается
   текущая задача. Блокировка в MongoDB позволяет подхватить её заново.
3. **PDF не читается.** `web_analysis` возвращает явную ошибку для PDF;
   извлечение текста из PDF в планах.
4. **Wikipedia как резерв поиска** иногда отдаёт 403 при агрессивном лимите запросов
   с одного IP. Основной провайдер — Tavily.
5. **pCloud** с апреля 2026 не выдаёт токены по логину/паролю — нужен OAuth2 и запрос в поддержку. Используется Cloudflare R2.
